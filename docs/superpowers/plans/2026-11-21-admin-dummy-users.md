# Admin "Create dummy user" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A system admin creates a ready-to-use dummy Student or Coordinator from Users & Access, gets a generated password shown once, and can reset that password later.

**Architecture:** The admin API creates the Clerk user server-side (email verified, generated password). It then creates the app account, role and student profile or coordinator assignment in **one** database transaction through the existing admin repository `run()`. If the database step fails, the Clerk user is deleted. A dummy is recognised by its primary email containing `+clerk_test@`, so no migration is needed.

**Tech Stack:** TypeScript, `@clerk/backend`, Neon (`sql.transaction`), React, Vitest, Playwright UI suites in `tools/admin`.

**Spec:** the "Design" section below. It was agreed with the owner in chat on 2026-11-21 and there is no separate spec file.

## Design (agreed 2026-11-21)

- Roles: **STUDENT** and **COORDINATOR** only. Never SYSTEM_ADMIN.
- Data: login, role, and either a **student profile** or a **coordinator assignment**. No academic records.
- Password: **generated by the server, shown once**, never stored by the app, never logged. "Reset password" on a dummy account generates a new one and shows it once.
- The account works straight away: the email is verified at creation. If Clerk asks for a code on a new device, `424242` works because the email is a `+clerk_test` address on the Clerk development instance.
- Email: `<slug>-<4 hex>+clerk_test@graduate.utm.my` (student) or `@utm.my` (coordinator). Slug = the name lower-cased, non `[a-z0-9]` runs → `-`, trimmed, max 20 chars, `dummy` when empty.
- Student profile:
  - name;
  - matric `DUMMY` + 6 digits (random);
  - the chosen curriculum (programme + version) and learning centre;
  - the **admin current semester**;
  - `weekly_working_hours = 0`, `available_study_hours = 20`.

  The profile is then COMPLETE (`apps/api/src/modules/profile/repository.ts:248-258`), so there is no setup step.
- Coordinator: one assignment (programme + learning centre, faculty taken from `programme.faculty_id`).
- Users list shows a **Dummy** badge. The dialog shows Clerk usage `N of 100`.
- Only SYSTEM_ADMIN can use any of this (the existing admin route guard).

## Global Constraints

- Allowed roles: `'STUDENT' | 'COORDINATOR'`. Any other value → 400 `INVALID_REQUEST`.
- Email marker: `+clerk_test@`. `isDummyEmail` is the only test for "is a dummy" anywhere.
- Clerk development user limit: `DUMMY_CLERK_USER_LIMIT = 100`.
- Password: 20 characters from `crypto.getRandomValues`, alphabet `ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz23456789!@#$%*-_`, at least one upper, lower, digit and symbol.
- Responses that carry a password send `Cache-Control: no-store`. The password never goes into an audit row, reason, log line or browser cache.
- The reason field follows the existing rule (`normaliseReason`, `ADMIN_REASON_MAX_LENGTH`).
- UI copy is plain English in the admin tone; follow `docs/themeguide.md` typography and run `assertReadable` in the new UI checks.
- No database migration; no new dependency.

## Review Focus

1. **Clerk user created, database step fails** (for example an inactive learning centre): the Clerk user must be deleted and the admin sees an error. No orphan login is left. Test in Task 4.
2. **No admin current semester**: student creation is refused with 409 `ACADEMIC_SEMESTER_UNAVAILABLE` **before** any Clerk call. Test in Task 4.
3. **Reset password on a real (non-dummy) account**: 409 `NOT_A_DUMMY_ACCOUNT`, and Clerk `updateUser` is never called. Test in Task 4.
4. **Clerk at 100 users**: 409 `DUMMY_LIMIT_REACHED` before creating. Test in Task 4.
5. **A name that is all symbols or non-Latin** (`"###"`, `"李明"`): the slug falls back to `dummy` and the Clerk first name keeps the original text. Test in Task 1.
