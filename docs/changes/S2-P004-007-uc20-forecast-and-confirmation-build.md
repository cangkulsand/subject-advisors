- **MT4 (forecast engine, `packages/shared/src/forecasting/engine/`).** Pure and deterministic; no HTTP, no DB. `runForecastEngine(input): ForecastEngineResult` in `forecast.ts`; `capacity.ts` (`resolveCapacityRule`, `evenSplit`, `allocateSections`), `demand.ts` (per student x subject evaluation), `policy.ts` (`isNearGraduation`, policy versions), `hash.ts` (stable JSON + non-cryptographic fingerprint), `types.ts`, `engine.test.ts` (36 tests).   - **Demand rules.** Skip passed (COMPLETED/EXEMPTED; a pass wins over other attempts, counted as `retakeResolvedAsPassed`). Semester rule applies only when the curriculum subject has `subject_semester_rule` rows (none = unrestricted). Mandatory prerequisites need a pass; when `conditionalPrerequisites` is AVAILABLE with an expression/conditions/topicDependent it supersedes the link rows (same as the pathway module), otherwise MANDATORY links are ANDed (RECOMMENDED advisory, COREQUISITE does not gate in v1). Three-valued logic: a prerequisite with no pass is NOT MET only when history is COMPLETE with no rejected rows and it is not IN_PROGRESS; otherwise unknown. A definite unmet prerequisite makes the student ineligible (not uncertain). Uncertain reasons (existing `UncertaintyReason` codes): HISTORY_UNKNOWN/PARTIAL, REJECTED_HISTORY_ROW, COHORT_STATUS_UNMAPPED (anything but ACTIVE), RETAKE_OUTCOME_UNRESOLVED (IN_PROGRESS attempt of the subject itself), PREREQUISITE_EVIDENCE_MISSING (IN_PROGRESS/unproven prerequisite, topic-dependent), CREDIT_EVIDENCE_MISSING (completedCredits condition not provable), CGPA_EVIDENCE_MISSING (cgpa conditions are always unknown). Credits earned = max recognized_credits per passed subject, else catalogue credits for COMPLETED; EXEMPTED with blank credits is unknown (never 0).

  - **Near graduation (policy v1, `policy.ts`):** supported eligible students whose remaining credits (curriculum `total_credit_required` minus credits earned) are <= 2 x target `max_credits`; unknown remaining credits never count. Information only.
  - **Allocation.** Rule by `class_type` and centre with precedence subject+centre, centre, global (only global rows exist today); NULL class type, no/ambiguous/invalid active rule gives CONFIGURATION_REQUIRED for that subject only. Sections = ceil(D / normal_maximum), even split (larger first, e.g. 46 -> 23+23, 71 -> 24+24+23); flags BELOW_MINIMUM (< minimum) and BELOW_OPTIMAL (< break-even); never cancels, never uses the exception maximum, `reviewStatus` PENDING. Quality: SUPPORTED (no uncertain), PRELIMINARY, INSUFFICIENT_DATA (D = 0 and uncertain > 0, no sections).

Mutations require `If-Match` (400 `IF_MATCH_REQUIRED`); order of checks: auth, header, body, run and scope (404), body scope equals stored scope (404), FINALIZED (409 `RUN_FINALIZED`), revision (412 `RUN_REVISION_MISMATCH`), lifecycle (409 `RUN_STATE_CONFLICT`), validation (422). The write is atomic against concurrency: the transaction first locks the run row, then a separate statement (fresh snapshot) raises a tagged cast error when status or audit count differ; the tag maps to 412.
  - **Decisions.** Allowed in DRAFT and UNDER_REVIEW; the whole batch is validated first and applied all-or-nothing (max 200, one decision per subject). A reason of 1-500 characters is required for every decision (422 `DECISION_REASON_REQUIRED`; the audit table needs it). REVIEW/APPROVE/DEFER set all sections of the subject to REVIEWED/APPROVED/DEFERRED (subject without sections: 422 `DECISION_NO_SECTIONS`). Replaced sections become REVIEWED. Each decision writes one `forecast_adjustment_audit` row (before-state from the validated read, after-state read back from the table inside the transaction, `approvalReference` inside the after-state).

Afterwards the 0001/0007 triggers refuse every write and the API answers 409 `RUN_FINALIZED`.
