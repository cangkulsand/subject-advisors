## 1. Plan

Test logins (such as the SECJH/SECRH mock users) were made with scripts. The owner asked for a way to create them from the admin menu. Agreed design (2026-11-21), with the full plan in `docs/superpowers/plans/2026-11-21-admin-dummy-users.md`:

- roles Student and Coordinator only;
- login and profile (student) or one coordinator assignment; no academic records;
- password generated by the server and shown once; "Reset password" makes a new one;
- the account works straight away.

No database migration: a dummy is recognised by its `+clerk_test@` email.

## 2. Implementation

- `packages/shared/src/admin/dummy.ts`: request types and validator, `isDummyEmail`, `dummyEmail`, `dummyMatric`, `DUMMY_CLERK_USER_LIMIT = 100`. `asRecord` in `admin.ts` is now exported. Five new error codes are added to `ADMIN_MUTATION_ERROR_CODES`.
- `apps/api/src/modules/admin/dummy-password.ts`: 20-character password from `crypto.getRandomValues`, with rejection sampling and at least one upper, lower, digit and symbol.
- `identities.ts`: `createUser`, `setPassword`, `deleteUser`, `userCount` (Clerk backend SDK).
- `repository.ts`: `createDummyAccount` and `currentSemesterId`.
  - Student, in one transaction: an account with the STUDENT role and a complete `student_profile` (admin current semester, matric `DUMMY` + 6 digits, hours 0 and 20).
  - Coordinator, in one transaction: the COORDINATOR role and one `coordinator_assignment` (faculty from the programme).
  - Guards reject a missing current semester and an inactive programme or learning centre before anything is written.
- `routes.ts`:
  - `GET /api/admin/dummy-users/capacity`.
  - `POST /api/admin/dummy-users`: checks the current semester and the Clerk limit first, then creates the Clerk user, then the account. If the database step fails, the Clerk user is deleted.
  - `POST /api/admin/users/{id}/dummy-password`: only for `+clerk_test` accounts.
  - Password responses are `no-store`.
- Web:
  - `DummyUserDialog.tsx` has the create form (shows Clerk usage) and the one-time credentials panel with Copy buttons and the `424242` hint, plus the reset dialog.
  - `AdminPages.tsx` adds the "Create dummy user" button, a Dummy badge in the list and on the account page, and a "Dummy account" card with "Reset password".
  - `client.ts` adds three methods; the credentials are never cached.
- Docs: `docs/api/admin-users.openapi.json` (three paths), `docs/clerk.md` (dummy users section), `README.md` (new row; the menu notes for Academic progress and Recommendations were corrected for S3-P004-023).

Decisions made during the build:
- **Reset password takes no reason** (a confirm only). Nothing could store the reason without a migration, so collecting it would mislead. Resets are therefore not in the application audit log.
- **Scope checks run as guards before the inserts.** A non-interactive transaction cannot check whether an earlier statement wrote a row.
- **The create dialog keeps the name "Create dummy user"** after success, for screen readers.

Final review (fresh reviewer, whole branch): no critical findings.
- Fixed: a dummy could be given System Admin through "Add role" and then have its password reset. `checkRoleEligibility` now refuses SYSTEM_ADMIN for any `+clerk_test` address (covers add, invite, grant and invitation redemption), and reset refuses accounts holding SYSTEM_ADMIN. Three tests added.
- For the owner: test code `424242` plus a guessable email is a weak second factor on a database shared with prod. This is documented in `docs/clerk.md`.
- Deferred minors (not fixed):
  - a failed Clerk clean-up is silent;
  - the capacity check can race;
  - resets have no in-app audit row;
  - Copy button feedback is not announced to screen readers;
  - focus is lost when the credentials appear;
  - the readability guard does not inspect the open credentials panel at 375px;
  - the "not active" message is shown for a programme with no faculty;
  - the new pill uses raw hex colours.
