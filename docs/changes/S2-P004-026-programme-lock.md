## 1. Plan

Problem: any student could change the programme (curriculum option = programme + version) on the profile page. SD FR-A3 says students cannot change it freely.

Product owner decision: **locked after first setup; only the admin changes it.**
- The student chooses the programme only when the profile is created. Once a profile exists, `PUT /api/profile` rejects a different `curriculumId` with `409 PROFILE_PROGRAMME_LOCKED` (re-sending the saved value is fine). The profile page shows the programme read-only with "Your programme is set. Contact the admin to change it."
- SYSTEM_ADMIN changes a student's programme from the Users & Access account detail (the account is the admin's handle on a student, and the page already holds the reason-dialog pattern, audit and toasts), with a required reason, recorded in an append-only audit.
- Effects: academic records reference `subject_id` and are kept. The student's saved semester picks (`semester_offering`, which reference `curriculum_subject_id` of the old curriculum) for semesters after the current one whose selection window has not closed are deleted in the same transaction and their number is returned ("Programme changed; N subject picks removed."). Picks of the current semester and of already closed windows are history and stay. Matric number, learning centre, current semester and profile data are unchanged.

Why a migration (0011): the existing guard trigger `preserve_student_curriculum` (0001, `db_preserve_membership()`) rejects any `student_profile.curriculum_id` change once the student has records, picks, plans or scenarios ("Controlled curriculum reconciliation required"). The admin change therefore needs a controlled, audited path through that guard. The audit itself reuses the existing append-only `academic_setup_audit_log` (no new public table).

Out of scope: the learning-centre lock pattern (the admin can change at any time), remapping picks to the new curriculum, plans/scenarios tables (not used by the application), applying 0011 anywhere. Rollback: drop `public.db_change_student_programme`, `migration_meta.programme_change_context` and restore the 0001 `db_preserve_membership()` body; revert the code. The audit rows stay (append-only).

## 2. Implementation

- **Migration `db/migrations/0011_student_programme_change.sql`** (additive, not applied anywhere): `migration_meta.programme_change_context(backend_pid, transaction_id, student_id)` (REVOKE ALL FROM PUBLIC); `CREATE OR REPLACE db_preserve_membership()` identical to 0001 except that the student-curriculum guard stands aside when a context row exists for this backend, transaction and student (same pattern as `db_set_current_semester` / `academic_switch_context`); `public.db_change_student_programme(target_student_id, target_curriculum_id) RETURNS integer` (EXECUTE revoked from PUBLIC): requires the trusted audit context (`db_academic_setup_context()`), locks the profile row `FOR UPDATE`, requires an active curriculum of an active programme, rejects an unchanged target, deletes the not-yet-closed future-semester picks of other curricula, inserts the context row, updates `curriculum_id`, removes the context row and writes the audit row (`entity_type='student_programme'`, `entity_id=student_id`, `action='CHANGE_PROGRAMME'`, actor, reason, before/after curriculum and programme, `removedPicks`, `removedSubjectIds`). Rule violations are `RAISE EXCEPTION 'PROGRAMME_CHANGE:<CODE>' USING ERRCODE='23514'` (no failing-cast guards). A semester counts as "not closed" when it is after the admin current semester and `selection_closes_at` is null or in the future.
- **DB tooling:** `manifest.json` (0011), `db/engineering-extensions.json` (0011 entry, no tables or columns), `db/checks/016_student_programme_change.sql` (new, 8 structural assertions) added to the `verify` list in `tools/db/cli.mjs`, to `tools/db/review.mjs` and to `tools/admin/test-academic-database.mjs`; `tools/db/migrations.test.mjs` (versions to 0011, new `0011 follows the exact 0010 prefix ...` test, 0010 test made position-independent). Table and FK counts in `001`/`005` are unchanged (no public table or FK is added).
- **Profile API (`apps/api/src/modules/profile/repository.ts`):** `save` reads the saved `curriculum_id` with the centre; a different curriculum on an existing profile throws `409 PROFILE_PROGRAMME_LOCKED` ("Your programme is set. Contact the admin to change it.") before any write. The upsert no longer writes `curriculum_id` on conflict and has `DO UPDATE ... WHERE student_profile.curriculum_id = EXCLUDED.curriculum_id`, so even if an administrator moves the programme between the check and the write nothing is overwritten; an empty result re-reads the profile and answers the same 409. Creation and re-sending the saved value are unchanged. The profile repository has no transaction or row lock (it issues single statements), so the lock is atomic in the single upsert statement rather than inside a transaction.
- **Profile web:** `ProfilePage.tsx` shows the saved programme as a read-only field with the help text (`aria-describedby`) once a profile exists; the select is shown only during setup; the saved curriculum id is sent unchanged (a saved curriculum that is no longer offered to new students no longer blocks saving). `client.ts`: `fresh` read option, `programme-admin-change-v1` contract marker on the profile and options cache keys, and a `409 PROFILE_PROGRAMME_LOCKED` response clears the academic snapshots; `data-cache.ts`: `dropAcademicEntry`, and `pruneStorage` collects keys before removing them (a latent bug: removing by index while iterating skipped keys because Chrome reorders Web Storage keys after a removal, which could leave a stale records snapshot after a save).
- **Admin API (`apps/api/src/modules/admin/`):** `GET /api/admin/users/{id}/programme` (student programme or null; 404 for an unknown account), `PATCH /api/admin/users/{id}/programme` (`{ curriculumId, reason }` -> `{ programme, removedPicks }`), `GET /api/admin/curriculum-options` (active curricula of active programmes). Repository: `studentProgramme`, `curriculumOptions`, `changeStudentProgramme` (one `sql.transaction`: audit context, account guard, `db_change_student_programme`, refreshed read). New codes in `errors.ts`: `STUDENT_PROFILE_NOT_FOUND` (404), `CURRICULUM_UNAVAILABLE` (409), `PROGRAMME_UNCHANGED` (409), mapped from the PostgreSQL messages. Shared: `AdminStudentProgramme`, `AdminCurriculumOption`, `AdminChangeProgrammeRequest`, `AdminProgrammeChange`, `validateChangeProgrammeRequest` (reason 1-500 characters, integer curriculum id, unknown fields rejected).
- **Admin web:** `StudentProgrammeCard.tsx` on the account detail (`AdminPages.tsx`): shown only for accounts with a student profile (student, matric number, programme, curriculum version) with a "Change programme" button; the dialog reuses `ReasonDialog` (new `disabled` prop) with a select of the other active programmes, the required reason, confirm, inline server errors, and a toast "Programme changed; N subject picks removed." `client.ts` (+ tests): `studentProgramme`, `curriculumOptions`, `changeProgramme` with strict decoders.
- **Tests added:** `profile/repository.test.ts` (creation, change rejected before any write, same value, upsert never rewrites `curriculum_id`, concurrent admin change); `admin/routes.mutations.test.ts` (the generic route matrix now covers the new PATCH: auth 401/403, content type, body validation, actor from the verified session, rule-error mapping; plus programme-specific cases: reason required, invalid ids, 405 with Allow, GET/null/404, options access); `admin/mutations.test.ts` (transaction shape, blank reason, error mapping, reads); `web/admin/client.test.ts`; `web/profile/data-cache.test.ts` (fresh read replaces the snapshot, 409 clears snapshots); browser `tools/p001/test-ui.mjs` (+3: read-only programme with help and unchanged curriculum id sent, select during setup, server 409 message with draft kept), `tools/admin/test-ui.mjs` + `fixtures.mjs` (+1: card shown/hidden, change dialog, reason, server error, toast with removed picks, 0 picks); `tools/integration/test-ui.mjs` (setup mock returns no profile, cache-reuse expectation updated for the fresh profile read); new `admin/student-programme.database.test.ts` (skips without `ADMIN_TEST_DATABASE_URL`: picks of open future semesters removed, current and closed kept, records kept, audit row, rejected cases, direct update still blocked, audit append-only).
- **Cache check (`docs/cachingguide.md`, rule 10):** server reads use the live profile (profile options resolve the curriculum from `student_profile` each time; offerings and forecasting scope read it live; the Redis curriculum bundle is keyed by curriculum, so no server invalidation is needed). The browser profile snapshot has no timed expiry, so the profile page now rereads `/api/profile` and `/api/profile/options` every time it opens (it no longer reuses the stored snapshot) and the cache keys carry a new marker; the offerings marker (`p002-context-v6-approved-offerings`) is unchanged because its shape did not change. Other pages show the new programme after the next profile page visit, the next write, or the 5-minute option/offering expiry; `PUT` validations are always live.
- **Docs:** `docs/api/admin-users.openapi.json` (two paths, schemas, error codes), `docs/database/data-contracts.md`, `docs/database/migrations.md`, `docs/cachingguide.md`, `README.md`.
- **Design notes / deviations:** (a) the task text assumed the profile PUT runs in a transaction that locks the row; it does not, so the lock is the conflict-guarded single statement described above. (b) The change is audited in `academic_setup_audit_log`, which is written by the database function, not by a trigger; it is not shown in the account's Users & Access audit list (that list reads the role and access logs only). (c) The learning-centre lock does not apply to the admin change. (d) A student whose saved curriculum was deactivated still cannot save the profile (the upsert requires an active curriculum, as before); the admin moves them to an active programme.
